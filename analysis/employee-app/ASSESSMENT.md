# Assessment: employee-app

- **Date:** 2026-10-31
- **Source:** `legacy/employee-app` → `/Users/arun/Documents/Projects/Code-Modernisation/Employee_Managment_App` (repo root)
- **Intent:** transform to Spring Boot 3.4 + React 18, PostgreSQL schema unchanged, full feature parity (see `INTENT.md`)
- **Method:** `find` + `wc` (no `scc`/`cloc` installed) and decision-keyword counting for complexity. Three parallel agents (structure, technical debt, security), with findings checked against a full read of the source.

## Executive Summary

employee-app is a small Java 8 Servlet/JSP web app (about 1.0 KSLOC: 11 Java classes, 8 JSPs, 2 PostgreSQL tables). It does admin sign-up and login plus employee add, list, edit and delete. Structurally it is simple and low-risk to move. There is no SQL injection, every query is parameterised, and nothing reaches outside the repo. **Security risk is critical**, though: no page or endpoint checks the session, "login" is ID plus name with no password, sign-up is open to anyone, logout does nothing, and the employee list has stored XSS. The headline recommendation is to **Rearchitect via `transform`**: split it into a Spring Boot 3.4 REST API and a React 18 single-page app over the unchanged schema. Behaviour that must be kept is pinned first by `extract-rules`, and about eight quirks need a human keep-or-fix decision before anything is built.

## Technical Debt (top 10 by remediation value)

1. **No authorisation, and logout does nothing.** There is no filter, no `web.xml` and no session check anywhere. `Welcome.jsp:53` only *displays* `adminName`. Logout POSTs to `index.jsp` (`Welcome.jsp:62-64`) and never invalidates the session.
2. **Authentication is ID + name only, and sign-up is open.**
   - `admin_data` has no credential column (`schema.sql:5-8`). Login is `WHERE id = ? AND name = ?` (`dao/AdminDAO.java:32`).
   - Sign-up accepts a blank or null name (`servlet/SignUpServlet.java:35`).
   - Because the schema is off limits, adding a password needs an explicit decision (see `brief`).
3. **Two login paths.** The form posts to `Login.jsp`, whose scriptlet does the login (`Login.jsp:66,76-94`). `LoginServlet` is dead but differs: no `NumberFormatException` guard (`:22`) and different error text (`:32`). Neither trims the name, although sign-up trims it on insert (`SignUpServlet.java:35`).
4. **DAOs swallow exceptions.**
   - `catch (Exception) { printStackTrace(); return false/null; }` in 6 methods, e.g. `dao/EmployeeDAO.java:55-58` and `:96-98` (`getAllEmployees` returns `null`, which the list page shows as an empty table).
   - A database outage therefore looks like "not found" or "invalid login".
   - Unguarded `Integer.parseInt` gives HTTP 500 at `DeleteEmployeeServlet.java:27` and `EditEmployeeServlet.java:29`.
5. **Delete and edit behaviour bugs.**
   - Delete's "not found" alert is overwritten by `sendRedirect` (`DeleteEmployeeServlet.java:32-34`), so a failed delete looks like a success.
   - Edit requires a name but never uses it (`EditEmployeeServlet.java:27-29`).
   - Edit accepts negative, NaN and Infinity salaries, which Add rejects (`EmployeeDAO.java:44` vs `AddEmployeeServlet.java:49`).
   - The session flash `message` is written (`DeleteEmployeeServlet.java:30`, `EditEmployeeServlet.java:33`) but never read.
6. **Money stored as DOUBLE, and the IDENTITY columns are bypassed.**
   - Salary is `DOUBLE PRECISION` / `double` throughout (`schema.sql:14`, `model/Employee.java:7`). It renders as `15000.0` or `1.0E7` (`showEmployee.jsp:35`).
   - IDs are always user-supplied (`EmployeeDAO.java:21-24`), so the identity sequences never advance. Switching to `@GeneratedValue` would collide with existing rows unless the sequences are reset.
7. **Responses are inline `<script>alert()` strings.** There are about 11 call sites across all servlets (e.g. `AddEmployeeServlet.java:72,81`). These do not translate to REST. Stored XSS through `<%= %>` at `showEmployee.jsp:33-34`. No CSRF protection.
8. **Hardcoded config.**
   - JDBC URL, username and an empty password in `context.xml:10-12`.
   - A misspelled, dead `path="/EmployeeManagmentApp"` (`context.xml:2`).
   - A machine-specific `tomcat.home` (`build.xml:11`).
9. **Platform coupling.**
   - `javax.servlet` in all six servlets.
   - A JNDI static initialiser (`util/DBUtil.java:16-23`) that turns into `NoClassDefFoundError` after one failure.
   - No dependency injection (`new EmployeeDAO()` on every request). `AdminDAO.saveAdmin` is static.
   - No tests.
10. **Dead code, logic in JSPs, duplicated CSS, template residue.**
    - Unused: `AdminDAO.addAdmin` (`:14`), `getAdminById` (`:47`), `EmployeeDAO.validateEmployee` (`:108`).
    - Unused imports (`signup.jsp:1`, `Welcome.jsp:3`, `LoginServlet.java:8`).
    - Styles copied inline across 4 JSPs.
    - NetBeans license headers in every servlet.

## Documentation Gaps (top 5)

1. **Authentication model.** The README says "admin authentication" and "session management" (`README.md:5,8`). In reality there is no password and no access guard, logout is fake, and `LoginServlet` is dead while `Login.jsp` does the work.
2. **Real code layout and entry points.** The README shows `src/main/java/...` (`README.md:29-54`), but the sources are flat `dao/ model/ servlet/ util/`. It also lists 4 servlets; there are 6 (`LoginServlet` and `SignUpServlet` are missing).
3. **DAO API.** The README documents `updateEmployee(id, name, field, newValue)` and `getEmployeeById` (`README.md:119,121`). The real method has no `name`, and `getEmployeeById` does not exist. It also doesn't explain that edit matches on ID only while delete matches on ID **and** name.
4. **Validation rules and error behaviour.** The README says "form validation" (`README.md:13`). Nowhere does it say which rules are server-side (Add: required fields, integer ID, salary ≥ 0, duplicate ID → 23505 message), which exist only in HTML5 attributes, or how errors appear (JS alerts, or a silent redirect on delete).
5. **ID ownership and data types.** Nothing explains that IDs are typed in by the user even though the columns are IDENTITY (so the sequences never advance), or that salary is a floating-point value. Both matter for any migration that keeps the schema.

## Recommended Modernization Pattern

**Rearchitect → `/code-modernization:modernize-transform`**

The language stays Java, but the architecture changes. A server-rendered Servlet/JSP monolith becomes a Spring Boot 3.4 REST API (Spring Security, Spring Data JDBC or JPA mapped onto the existing tables) plus a React 18 single-page app. A same-stack `uplift` (javax → jakarta, Java 8 → 17/21) would leave the JSP scriptlets, alert-string responses and missing security model untouched, and would not reach the stated React target. A from-scratch `reimagine` is unnecessary, because the domain is tiny, the schema is fixed, and every behaviour can be pinned and carried across.

`transform` fits best. It moves one slice at a time: (1) persistence and the `Employee` read path, (2) employee add/edit/delete, (3) identity, login and session. Each slice gets equivalence tests against the legacy app, which builds and runs locally (preflight Check 3). That is exactly the evidence the "nothing missed" goal needs.

**Before the build, `review` and `brief` must settle these:**
- password storage despite the schema freeze
- open sign-up
- user-assigned IDs vs IDENTITY
- edit-by-ID-only vs delete-by-ID+name
- negative salaries on edit
- the swallowed delete error
- the unused flash message
- DOUBLE salary formatting
