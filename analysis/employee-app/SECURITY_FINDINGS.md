## Context: what the modernization deliberately kept

The missing authentication (SEC-001, SEC-004..SEC-008, SEC-010, SEC-011) is the behaviour the user confirmed as **Right** for parity in RULE_REVIEWS (RULE-016, RULE-017, RULE-018), so the modernized app in `modernized/employee-app/app/` has the same gaps by design. Applying this patch changes the legacy app's behaviour against those confirmed rules, and the equivalence evidence (EQUIVALENCE.json, VERIFICATION.md) was recorded without it. Whoever applies it decides whether the modernized app gets the same fixes.

No instruction-shaped text aimed at automated analysis was found in the source.

Credentials: no live secret value was found in the tree or the git history. The only database password (`webapp/META-INF/context.xml:12`) is empty. 2 credential-configuration findings (SEC-015, SEC-025) — inventory in SECRETS.local.md (gitignored; not for sharing).

## Patch Review

Independent review by the security-auditor agent, one verdict per hunk, looped until clean (at most 3 rounds). **Residual risks the reviewer asked to keep visible** (no code change after round 3):

- **The capped lockout table fails closed.** About 1,700 attacking addresses (easy within one IPv6 /64) could fill its 10,000 keys and block every new login while they keep it up. Option for a later pass: when full, still allow ip: keys and refuse only new id: keys. The cap can be overshot by a few entries (harmless race).
- **Per-id lock by a distributed attacker.** Anyone can lock a given admin id for 15 minutes (accepted price of the per-id limit).
- **Proxy deployments:** behind a reverse proxy without RemoteIpValve, every user shares one address, and 5 bad logins lock everybody out.
- **SEC-008 and SEC-011 stay open (High).** Without a real secret, each admin id allows 5 guesses per 15 minutes (about 480 a day) against a guessable name.
- **Sign-up bootstrap:** on an empty admin_data, whoever reaches signup.jsp first becomes admin; create the first admin before exposing the app.
- **The parity note above records a decision; it does not argue against hardening.** The modernized app has the same gaps by design, and these fixes should be considered for it too.
